## Finding 1: The "conservative" empty definition cannot see ANY of the three incident screens the phase exists for
- **Severity:** Critical
- **Location:** Phase 1, section "Architecture" (empty definition) + "Implementation Steps" step 2
- **Flaw:** Phase 1 defines empty as `Array.isArray(p) && p.length === 0 || p == null` at top level and explicitly EXCLUDES object payloads — citing `{items: [], total: 0}` as the false-positive shape to avoid. But all three F1/F2/F4 incident screens return exactly that object shape:
  - F1 `/finance/class-placement`: `classBatch.list` returns `{items, total, page, pageSize}` — object, never a top-level array
  - F2 `/teaching/grading`: `submission.listForGrading`, page reads `data?.items`
  - F4 `/hr/payroll`: `user.pickList`, page reads `data?.items`
  The shape the Architecture section dismisses as a false positive IS the true-positive shape of every screen in the expectation seed list.
- **Failure scenario:** `screen-role-expectations.ts` declares `classBatch.list` / `submission.listForGrading` / `user.pickList` as `nonEmpty`. Capture runs against an empty DB; all three return `{items: []}`; the empty flag stays `false`; `emptyButExpected` stays `[]`. Falsification B (the phase's self-declared "tiêu chí quan trọng nhất") can never go red on the declared screens. The phase ships a detector that is structurally blind to the F2-class incident it was built after, and everyone reads green.
- **Evidence:** `apps/api/src/class/class-batch-router.ts:269-274` (`return { items: ..., total, page, pageSize }`); `apps/admin/src/pages/teaching/grading.tsx:258,264` (`listForGrading` → `data?.items ?? []`); `apps/admin/src/pages/hr/payroll.tsx:417-419` (`user.pickList` → `data?.items ?? []`); `apps/admin/src/pages/enrollment/class-placement.tsx:51-52,60` (`classBatch.list` → `classBatchData?.items ?? []`).
- **Suggested fix:** Invert the rule: for the declared list procedures, treat `{items: []}` (or any single array-valued field named in the expectation) as empty. Cheapest safe form: expectation entries carry an optional `listField: 'items'`, defaulting to top-level-array. Do not ship Phase 1 until Falsification B goes red on all three declared screens.

## Finding 2: Falsification B and the "green" run use the same DB state — the seed provides business data for none of the three screens
- **Severity:** Critical
- **Location:** Phase 1, "Implementation Steps" 5–6 + "Architecture" (seed policy) vs plan.md "Acceptance Criteria"
- **Flaw:** Step 5 requires `emptyButExpected ≠ rỗng` on an unseeded DB; step 6 requires both finding arrays empty "với seed chuẩn". But the standard seed (`synthetic-seed-env.sh:87` → `packages/db/prisma/seed.mjs`) creates only: 2 facilities, 2 CurriculumUnit rows, and the shift catalog (`seed.mjs:39-46,64-68,80-125`). No ClassBatch, no Student/Submission, no data feeding `classBatch.list`, `submission.listForGrading`, or the payroll roster beyond capture's own `capture-<role>` AppUsers. "Seeded" and "unseeded" are indistinguishable for every expected procedure — steps 5 and 6 are mutually exclusive. The phase's own escape hatch ("màn nào seed hiện tại chưa cho dữ liệu thì chưa khai kỳ vọng — ghi TODO") then forces all three incident screens to TODO, directly contradicting the phase requirement "khởi điểm phủ 3 màn sự cố thật" and the plan-level AC "Expectations phủ tối thiểu 3 màn của F1/F2/F4".
- **Failure scenario:** Implementer reaches step 6, sees `emptyButExpected` permanently non-empty (or, per Finding 1, permanently empty), and resolves it the only way the constraints allow: deletes the F1/F2/F4 expectations and writes TODOs. The plan ships with the AC checkbox unticked or quietly reinterpreted — the classic phantom-gate outcome the plan claims to be fighting.
- **Evidence:** `scripts/synthetic-seed-env.sh:85-87` (seed = `node packages/db/prisma/seed.mjs` only); `packages/db/prisma/seed.mjs:36-50` (facilities + curriculum + shift catalog, nothing else); `apps/e2e/tests/screen-role-capture.ui.spec.ts:112-117` (capture seeds only AppUsers). Contradiction targets: phase-01 step 2 vs risk row 3; plan.md AC line "Capture ghi `empty`... phủ tối thiểu 3 màn của F1/F2/F4".
- **Suggested fix:** Either (a) drop the "no new seed" constraint and add a minimal deterministic business seed (1 ClassBatch, 1 Submission, N staff) to the synthetic-seed path, or (b) rescope the AC honestly to "expectations cover whichever screens the current seed can feed" and name them. The plan cannot keep both the constraint and the AC.

## Finding 5: Negative-assertion journeys (6, 8, 10) have no supported mechanism — both Phase 4 helpers are specified to FAIL on absence
- **Severity:** Medium
- **Location:** Phase 4, Requirements (helper contracts) vs Phase 5, table rows 6/8/10 + step 2
- **Flaw:** `menuNav` is specified to "fail nếu entry không hiện với vai đó" and `findInList` to fail when the object isn't found. But journeys 6 ("sale KHÔNG tự duyệt được"), 8 ("GĐĐT không duyệt được phiếu sale"), and 10 ("sale KHÔNG thấy entry Quà tặng") are absence assertions — the exact inversion of both contracts. Worse for journey 8: `manualPunch.list` filters the inbox to the caller's own track (`sale→GĐKD, giao_vien→GĐĐT`), so GĐĐT never even sees the sale ticket — the observable is "ticket absent from list", which `findInList` by contract reports as a test failure, not a pass.
- **Failure scenario:** Implementer needs a not-found result to be green in three specs and a red in every other spec, with helpers that only express red-on-absence. The realistic outcome is ad-hoc raw-locator assertions bypassing the helpers in exactly the specs where the §4.2/§4.3 discipline matters most — or `expect(findInList(...)).rejects` patterns that pass on ANY failure (timeout, wrong page), i.e. phantom negative tests.
- **Evidence:** `apps/api/src/checkin/router.ts:395,417-436` (inbox scoped to caller's track — cross-track tickets never listed); phase-04 Requirements ("fail nếu entry không hiện", "không nhận id"); phase-05 rows 6/8/10.
- **Suggested fix:** Add explicit absence APIs to the Phase 4 helper spec (`menuNav.assertEntryAbsent(label)`, `findInList.assertAbsent(predicate)` with a bounded, settled-state wait) so a negative result is a first-class green, and note for journey 8 that the UI-observable is list-absence, not a denied approve click.

## Finding 6: Phase 3 misstates the worker's boot posture and ignores its existing health endpoint
- **Severity:** Medium
- **Location:** Phase 3, "Overview" ("worker không có boot-check") + Requirements check 1
- **Flaw:** The worker runs a full boot-check suite before its drain loop (`assertAllowDevAuthNotInProd`, `assertLmsSecretConfiguredForProd`, `assertCmcAppNotSuperuser`, `assertCmcAppRole`) — the actual documented gap is only that `assertRequiredEnvForProd` (Brevo env) runs API-side only (đợt B phase-02's noted limitation). The plan's unqualified claim will mislead the implementer. Separately, check 1 proposes "docker compose ps + log marker" while the worker already exposes an HTTP health endpoint that tracks consecutive drain failures, and prod compose already wires a healthcheck against it — a strictly stronger signal than any boot log line (of which, in production, the only stable one is `[worker] health endpoint listening...`; the ConsoleTransport marker at `index.ts:108` never prints in prod).
- **Failure scenario:** ops-smoke greps for a log marker that doesn't exist in prod output (or exists only once at boot, rotated away), reports FAIL/flaky on a healthy worker, and the script loses credibility in its first host runs — the "gate someone deletes" failure mode the plan quotes from ci.yml.
- **Evidence:** `apps/api/src/worker/index.ts:135-140` (boot-check suite), `:48-66` (health endpoint + drain-failure tracking), `:108` (non-prod-only marker); `docker-compose.prod.yml:98-103` (worker healthcheck `wget http://localhost:3001/`); `plans/260723-0913-don-tien-uat-truoc-phase-4/phase-02-boot-check-brevo-key-shape.md:63` (the real, narrow limitation).
- **Suggested fix:** Reword the overview to the precise gap (worker lacks `assertRequiredEnvForProd` only). Check 1 should read the compose healthcheck status (`docker compose ps --format json` → `Health`) as the worker-liveness signal and drop the log-marker requirement to a supplementary FATAL-grep.

## Finding 7: "Enqueue qua một procedure sẵn có" — no such procedure exists; the only path replicates an internal payload contract by hand
- **Severity:** Medium
- **Location:** Phase 3, "Architecture" (mục 5 email path)
- **Flaw:** The architecture presents two options: an existing enqueue procedure, or raw psql insert. The first option does not exist — the only `emailOutbox.create` call sites are receipt approval (`finance/router.ts:1106`) and LMS OTP (`lms-auth/router.ts:418`); there is no generic/test enqueue procedure. That leaves only the psql insert, whose `payload` Json must satisfy `renderOutboxEmail`'s kind discrimination (receipt/otp/fallback) — an internal contract the shell script would hardcode and silently break the day templates change. An `otp`-kind payload additionally risks the stale-OTP scrub sweep mutating the row mid-smoke.
- **Failure scenario:** Script inserts a guessed payload; worker renders the empty fallback or dead-letters after `EMAIL_MAX_ATTEMPTS`; smoke reports FAIL on a healthy mail path — or a template refactor breaks ops-smoke with no test pointing at why.
- **Evidence:** grep `emailOutbox.create` in apps/api/src → only `finance/router.ts:1106`, `lms-auth/router.ts:418`; `apps/api/src/worker/email-transport.ts:59,150` (`renderOutboxEmail(email.payload)`); `apps/api/src/worker/relay-email-outbox.ts:67-71,111-125` (OTP-kind scrub sweep).
- **Suggested fix:** Delete the phantom option from the architecture; decide NOW that mục 5 inserts a row and pin the payload shape by generating it from the exported template types (a tiny `tsx -e` snippet importing `email-templates.ts`), not a hand-written JSON literal in bash.
