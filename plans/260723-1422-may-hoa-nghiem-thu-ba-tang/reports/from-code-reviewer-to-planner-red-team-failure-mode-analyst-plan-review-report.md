## Finding 1: Capture and journeys have no executor — nothing in CI ever runs them, so the promotion condition is unsatisfiable by construction
- **Severity:** Critical
- **Location:** Plan-wide — plan.md "Sau plan này" (lines 90-94), Phase 1 entire, Phase 5 "Architecture" (lines 42-44)
- **Flaw:** The plan's promotion ladder is "mỗi tầng warn ≥2 tuần **chạy trong CI**, báo-giả ~0 ⇒ gỡ continue-on-error" (plan.md:92-93). But no CI job runs the capture or the journeys, and the plan never adds one. The CI e2e job runs plain `pnpm --filter @cmc/e2e test` (ci.yml:152) without `PLAYWRIGHT_UI=1`; the Playwright config explicitly documents that this default run is **API-only** — the `ui-chromium` project only registers under `PLAYWRIGHT_UI=1` (playwright.config.ts:14-18, 73-84). So `screen-role-capture.ui.spec.ts` — including all of Phase 1's new `emptyButExpected`/`silentScreens` findings — executes only when a human remembers the incantation locally. Phase 5 then asserts "Kết quả chạy journey là việc của CI job e2e" (phase-05:43-44) — factually false against ci.yml as it stands — and open question #2 *defers* the one decision that determines whether tầng A/B ever executes automatically.
- **Failure scenario:** Phase 1 lands, falsifications pass once on the author's machine, plan closes DONE. Next month someone renames a procedure or reshapes a payload; no pipeline runs capture; expectations silently rot exactly like `screen-role-matrix.json` did (nợ N5 — drifted because "không CI nào regenerate", phase-02:14-16). Meanwhile the warn-data clock for promotion never starts because there are zero CI runs to measure — permanent warn, permanent theater. This is lie #5 in the making: a net that no pipeline runs catches nothing while the plan's AC table reads all-green.
- **Evidence:** `.github/workflows/ci.yml:151-152` (e2e runs `pnpm --filter @cmc/e2e test`, no `PLAYWRIGHT_UI`); `apps/e2e/playwright.config.ts:14-18, 73-84` ("A plain `playwright test` (the default CI e2e job) is therefore API-only"); `plans/.../plan.md:92-94`; `plans/.../phase-05-journey-10-luong-loi.md:43-44`.
- **Suggested fix:** Deciding the executor is a *precondition*, not open question #2. Add to Phase 1 and Phase 4 scope: a CI job (or scheduled workflow) that sets `PLAYWRIGHT_UI=1`, installs browsers, and runs capture + journeys, warn-only. Without it, strike the promotion ladder from the plan — it cannot be honest.

## Finding 2: Phase 1's expectations have no data source — the seed contains none of the F1/F2/F4 business data, and capture runs in a facility the seed never touches
- **Severity:** Critical
- **Location:** Phase 1, sections "Architecture" (lines 37-41), "Implementation Steps" 2/5/6, Success Criteria
- **Flaw:** Two stacked factual errors. (a) Phase 1 says business data (lớp, học viên) comes from "seed của `synthetic-seed-env.sh`" — but that script just runs `packages/db/prisma/seed.mjs`, which seeds only: two Facility rows, 2 global CurriculumUnit rows, and a shift catalog. **No ClassBatch, no students, no enrollments, no staff/payroll rows** — nothing that makes `/finance/class-placement` classBatch/list, the `/teaching/grading` class dropdown, or the `/hr/payroll` roster non-empty. (b) Even if it did, capture sessions are minted with `facilityId = process.env.E2E_FACILITY_ID` — the **ephemeral facility** `global-setup.ts` creates fresh per run (`E2E Run <timestamp>`), which is a different facility from the seed's dev facility; RLS facility-scoping guarantees capture sees zero of the seed's rows. Consequences: step 6 ("run chuẩn → cả hai mảng finding rỗng") is unachievable; AC "Expectations phủ ≥3 màn F1/F2/F4" collides head-on with the constraint "KHÔNG chế seed mới" plus the escape hatch "màn nào seed chưa cho dữ liệu thì chưa khai kỳ vọng" — following the escape hatch means declaring expectations for **zero** of the three incident screens, failing the AC. And Falsification B loses all discriminating power: the "unseeded" run and the "seeded" run produce identical `emptyButExpected` output, so B is red in both — a falsification that cannot distinguish broken from working measures nothing.
- **Failure scenario:** Implementer hits the contradiction mid-phase and resolves it the cheap way: declares expectations only for screens the capture's own `seedAppUser` rows accidentally satisfy (e.g. `/hr/payroll` roster = the 5 capture users themselves), writes TODO for F1/F2, ticks the AC box "≥3 màn" with a footnote. The two screens whose silent-empty failure mode motivated the entire phase (F1 class dropdown, F2 grading dropdown) remain exactly as unmeasured as they were for 16 days.
- **Evidence:** `packages/db/prisma/seed.mjs` (full read: `upsertFacility` ×2, `seedCurriculumUnits`, `seedShiftCatalog` — nothing else); `scripts/synthetic-seed-env.sh:85-87` (seed = `node packages/db/prisma/seed.mjs`); `apps/e2e/src/global-setup.ts:115-120` (fresh facility per run → `E2E_FACILITY_ID`); `apps/e2e/tests/screen-role-capture.ui.spec.ts:43, 113-117, 130` (identities and cookies bound to that facility); `plans/.../phase-01-capture-data-shape.md:38-41, 53, 56-57, 63-65`.
- **Suggested fix:** The phase must either (i) admit a minimal business-data seed **inside the capture's facility** (a small fixture step after `seedAppUser`, same file, ~1 class + 1 student + 1 submission) as in-scope, or (ii) cut F1/F2 from the AC honestly. Option (i) is the only one that keeps the phase's stated purpose. Also re-specify Falsification B as "delete the fixture rows, rerun" so it actually flips a green run to red.

## Finding 3: `silentScreens` is built on a racy recorder — the new finding class will generate false alarms that poison the very metric promotion depends on
- **Severity:** High
- **Location:** Phase 1, "Requirements — Functional" finding class (b), step 3
- **Flaw:** The capture's response handler is fire-and-forget: `void response.json().then(...)` with no await and no settling barrier before `await context.close()` 1.2 s after `domcontentloaded` (a fixed `waitForTimeout(1_200)`). Records for late responses are dropped nondeterministically. Today that only undercounts. Phase 1 turns "zero records for a (path, role) pair" into a **finding** (`silentScreens`) — converting an existing benign race into a false-alarm generator. A slow first navigation (cold preview server, CI runner under load) fires its calls after the 1.2 s window or has its `json()` promise still pending at `context.close()` → pair recorded as "màn câm lặng" when the screen called fine.
- **Failure scenario:** Warn output flip-flops between runs: `/finance/class-placement [sale]` silent on Tuesday, clean on Wednesday, no code change. Per Q4 the gate needs "báo-giả ~0" to promote — the race guarantees báo-giả > 0, so either the gate never promotes (finding 1's rot) or someone "fixes" flakiness by widening timeouts until the sweep exceeds its own 20-minute budget (`test.setTimeout(20 * 60 * 1000)`, spec line 104).
- **Evidence:** `apps/e2e/tests/screen-role-capture.ui.spec.ts:141-159` (`void response.json().then(...)`, unawaited), `:166-170` (`waitForTimeout(1_200)` then `context.close()`), `:104` (20-min sweep budget).
- **Suggested fix:** Phase 1 step 3 must include hardening the recorder before building findings on it: collect the per-page promises and `await Promise.allSettled(pending)` before `context.close()`, and make `silentScreens` require zero records across a retry, not a single pass.

## Finding 4: The `.journey.spec.ts` suffix matches the API project's testMatch — browserless CI will pick up every journey and fail it, silently
- **Severity:** High
- **Location:** Phase 4, "Architecture" (line 36); Phase 5, Related Code Files
- **Flaw:** The `api` project matches `/(?<!\.ui)\.spec\.ts$/` — the lookbehind only excludes `.ui.spec.ts`. `finance-receipt.journey.spec.ts` ends in `.spec.ts` not preceded by `.ui`, so it **matches the api project** and runs in the default CI e2e invocation — a run with no `PLAYWRIGHT_UI`, no preview servers, and no `playwright install` step in the job (ci.yml e2e job steps 123-152 contain none). Every journey errors on browser launch. The job is `continue-on-error: true` at the **job** level (ci.yml:104), so the wreckage is invisible.
- **Failure scenario:** Phase 4 lands; from that commit forward the e2e CI job fails on every push, masked by continue-on-error. The one job that is supposed to be "easy to promote to a blocking gate once … stable" (ci.yml:99-101) is now permanently red for a structural reason, making promotion of the *API* e2e suite impossible too — Phase 4 quietly destroys another gate's promotion path as collateral.
- **Evidence:** `apps/e2e/playwright.config.ts:69` (`testMatch: /(?<!\.ui)\.spec\.ts$/`); `.github/workflows/ci.yml:102-104, 122-152` (job-level continue-on-error; no browser install; plain `pnpm --filter @cmc/e2e test`); `plans/.../phase-04-journey-infra-hoi-quy.md:36`.
- **Suggested fix:** Name journeys `*.journey.ui.spec.ts` (excluded by the existing lookbehind, matched by ui-chromium's `/\.ui\.spec\.ts$/`), or tighten the api testMatch. Must be an explicit step in Phase 4, with a check that the default `playwright test --list` does not include journeys.

## Finding 5: Phase 2 warn-first does not close N5 — drift still merges, and the promotion ritual has a proven-dead precedent and no owner

- **Flaw:** N5 is "matrix trôi âm thầm vào main". - **Failure scenario:** Week 3 after landing: a nav entry is added in a PR, author ignores the yellow annotation, merge. Matrix on main lacks the new (screen, role) pairs. The next local capture run reports "0 denied, 0 emptyButExpected" over a matrix that no longer covers the new screen — all-green over a shrunken universe. Make this one step blocking from day 1 (fail = "run regen, commit"), or if warn-first is kept for uniformity, name an owner and a calendar date for the promotion review in the plan's AC.

Run journey falsifications via `playwright test <spec>` only, so the signal is unconfounded.

## Finding 7: ops-smoke's SKIP-exit-0 and 3-minute mailbox poll collide with the runbook's gates in both directions
- **Severity:** Medium
- **Location:** Phase 3, Requirements items 5-6, "Non-functional" exit-code spec (line 31), step 5
- **Flaw:** Two opposite failure modes share one exit code design. **Direction 1 (false green):** `OPS_SMOKE_SKIP_MAILBOX=1` → exit 0. Phase 3 step 5 then rewires runbook §3.0 to "bằng chứng bước 0 = output `ops-smoke.sh`". An operator under time pressure sets the skip flag, gets exit 0, and files it as bước-0 evidence — while §9's gate explicitly requires "**ảnh chụp hộp thư**, không phải mã 2xx của transport" (runbook:335), a lesson bought with a 12-day Brevo 401. A gate you can turn off with an env var, whose SKIP appears only in a summary nobody is required to archive, will be turned off. **Direction 2 (false red):** the mailbox check polls Graph for 3 minutes then FAILs → exit ≠ 0. Graph message-list indexing latency routinely exceeds 3 minutes; a healthy deploy now "fails smoke" — and the runbook's redeploy-once rule (runbook:59: a second deploy breaks the §9 commit-hash gate and forces an e2e rerun) means the operator's choices are: break the hash gate, or learn to ignore the tool. Bonus: every debug retry sends a real Brevo email against the 300/day free quota already flagged in đợt B (phase-03-brevo:166).
- **Failure scenario:** UAT morning. Smoke run 1: mailbox timeout, FAIL. Operator reruns twice (2 more real emails), still flaky. Third run with `OPS_SMOKE_SKIP_MAILBOX=1`: exit 0, screenshot of the green summary into the biên bản. §9's mailbox-photo line gets ticked off the strength of "smoke passed". Email path is unproven at go-live — the precise outcome §9 was hardened against.
- **Evidence:** `plans/.../phase-03-ops-smoke-host.md:25, 31, 57`; `docs/runbook-uat-golive.md:335` (photo not 2xx), `:59` (redeploy-once); `plans/260723-0913-.../phase-03-brevo-host-uat-email-that.md:166` (quota).
- **Suggested fix:** (1) Make SKIP structurally un-launderable: with the skip flag, print exit summary line `PASS-WITH-SKIP (NOT valid as §9 email evidence)` and have §3.0's pointer state that only a no-skip run counts. (2) Split exit codes: mailbox timeout → distinct code + "email SENT (worker log line X), receipt UNCONFIRMED — recheck manually" rather than a bare FAIL, since send-success and read-back-timeout are different facts.

## Finding 8: "Log không có FATAL từ lần boot gần nhất" is unimplementable as specified — docker logs outlive boots
- **Severity:** Medium
- **Location:** Phase 3, Requirements item 2
- **Flaw:** `docker logs` retains output across `docker restart`/in-container process restarts; only recreate clears it. "Từ lần boot gần nhất" needs an anchor (the worker's boot marker timestamp, or `State.StartedAt` + `--since`), and the phase specifies none. A naive `docker logs | grep FATAL` fails forever after one historical FATAL (a permanently red check gets ignored — gate-rot); a sloppy `--since` anchored to wall-clock misses a real FATAL from a crash-loop that restarted 10 minutes ago. This is the restore-drill lesson shape (`scripts/restore-drill.sh` sort|tail-1 picking the wrong dump — journal:31): a "latest X" selection whose definition of *latest* was never pinned.
- **Failure scenario:** Week 1 on the host, one transient FATAL during a Postgres hiccup. Every subsequent ops-smoke run FAILs item 2. By week 2 the operator's muscle memory is "item 2 is always red, ignore it" — and the run where FATAL is *new* looks identical.
- **Evidence:** `plans/.../phase-03-ops-smoke-host.md:22` ("không có `FATAL` từ lần boot gần nhất" — no anchor specified); `docs/journals/260722-260723-...md:31` (restore-drill "latest" trap precedent).
- **Suggested fix:** Specify the anchor in the phase: `docker inspect -f '{{.State.StartedAt}}'` per container → `docker logs --since <that>`, and note in the script header that a *process* restart inside a container is invisible to this anchor (accepted limitation, stated per the repo's honesty convention).
