# Red-Team Plan Review — Security Adversary

**Plan:** `plans/260723-1422-may-hoa-nghiem-thu-ba-tang/`
**Reviewer role:** Security adversary + fact-checker + contract verifier
**Date:** 2026-07-23
**Verdict:** Do not execute Phase 3 as written. Two Critical/High trust-boundary defects (tenant-wide mailbox read scope; RLS/validation-bypassing outbox insert with a defeatable guard). Phases 1/2/4/5 are lower-risk but carry a real secret-handling and contract gap.

## Finding 1: Granting Graph `Mail.Read` to the shared Entra app is a tenant-wide mailbox-read escalation, not a checkbox
- **Severity:** Critical
- **Location:** Phase 3, "Architecture" (mục 5, Graph read) and plan.md "Câu hỏi chưa giải" #1
- **Flaw:** The plan frames the Graph read step as a small gating question — "Graph app có quyền `Mail.Read` chưa?" — and treats a yes/no as sufficient to proceed. But the Graph transport authenticates via **client-credentials (application permissions)**, not delegated. `fetchAccessToken()` uses `grant_type: client_credentials` with `scope: .default` (`apps/api/src/worker/email-transport.ts:121-129`). Under application permissions, `Mail.Read` is **tenant-wide**: it authorizes reading *every* mailbox in the tenant, not just the sink. Worse, `scripts/env-check.sh:40` documents that **Entra shares its app with Graph email** (`# Staff SSO only enforced once enabled (Entra shares its app with Graph email)`), so the credential being widened is the same `GRAPH_CLIENT_SECRET` already loaded into the worker and API. The blast radius of a `GRAPH_CLIENT_SECRET` leak goes from "send mail as one sender" to "read all staff+student mail in the tenant."
- **Failure scenario:** Operator adds `Mail.Read` application permission to satisfy the smoke test's poll-mailbox step. `GRAPH_CLIENT_SECRET` later leaks (it is in `.env.prod`, loaded by the same worker that the plan wants to exercise on the prod host). Attacker now reads every mailbox in the tenant — HR, finance, leadership — a full PII/confidential-comms breach, all to let a smoke test confirm one email arrived.
- **Evidence:** `apps/api/src/worker/email-transport.ts:121-129` (client-credentials, `.default`); `scripts/env-check.sh:40` (shared app); `apps/api/src/boot-checks.ts:199` & `:243` (`GRAPH_*` are prod-required, live in `.env.prod`).
- **Suggested fix:** Do not add tenant-wide `Mail.Read` to the shared app. Either (a) use Graph **application access policy** (`New-ApplicationAccessPolicy`) to scope the app's mail access to *only* the sink mailbox, and document that constraint as a precondition; or (b) drop the mailbox-poll entirely and assert delivery via the outbox row transitioning to `sent` (the worker already records this) — the plan itself offers outbox assertion as the CI path (Q3), so the host smoke can reuse it without any read scope. The plan must state the exact scope/policy, not ask "does it have Mail.Read."

## Finding 2: Phase 3's "insert directly into EmailOutbox via psql" bypasses RLS + app validation, and the sink guard is defeated by the documented empty-domain config
- **Severity:** High
- **Location:** Phase 3, "Architecture" (mục 5: "insert trực tiếp row EmailOutbox transport `brevo` bằng psql (docker exec)") and Risk table row 4
- **Flaw:** Two compounding problems. (1) The direct-insert option writes an `EmailOutbox` row as the `postgres` superuser role, bypassing RLS and any application-layer validation entirely. `EmailOutbox.to` is a free-form `String` (`packages/db/prisma/schema.prisma:954`) and the worker's `relayEmailOutbox` will actually deliver `transport=brevo` rows to whatever `to` holds — a real send to a real address, with no audit trail of who enqueued it. (2) The mitigation ("guard từ chối nếu địa chỉ không thuộc `STAFF_EMAIL_DOMAIN`") silently no-ops in a supported prod configuration: `.env.prod.example:38` states `STAFF_EMAIL_DOMAIN` may be **left empty to allow all Entra users**, and `sso-routes.ts:212` confirms empty is a live mode (`console.warn('[sso] STAFF_EMAIL_DOMAIN is unset — all Entra users ... can log in')`). If the guard reads an unset/empty domain, it either matches nothing (rejects the sink too — smoke unusable) or is skipped (rejects nothing — smoke can send anywhere). The plan specifies neither behavior.
- **Failure scenario:** Operator runs ops-smoke on a prod host where `STAFF_EMAIL_DOMAIN` is unset (a documented, allowed config). The `to`-domain guard is a no-op, a typo or stale sink var points `to` at a customer/parent address, and the worker sends a real Brevo email to a real external recipient from the direct psql insert — with no audit record of the smoke test as the origin.
- **Evidence:** `packages/db/prisma/schema.prisma:954` (`to String`, free-form); `apps/api/src/worker/index.ts:93` (`brevo: new BrevoEmailTransport()` relays in prod); `.env.prod.example:38` (empty domain = allow all); `apps/api/src/auth/sso-routes.ts:212` (empty-domain warning path).
- **Suggested fix:** Drop the direct-psql-insert option; require enqueue through the real worker/outbox procedure so the audit path and app validation apply (the plan already prefers this — "ưu tiên đường đi qua worker thật" — so delete the psql escape hatch rather than leaving it as an option). Make the sink guard **fail-closed on an empty/unset `STAFF_EMAIL_DOMAIN`** (refuse to send, print SKIP), and pin the sink address to an exact allowlisted literal, not a domain-suffix check.

## Finding 3: `--local` mode claims row-count "PASS thật" as superuser `postgres`, but the plan never scopes least-privilege DB access on the prod host
- **Severity:** Medium
- **Location:** Phase 3, "Requirements" mục 6 ("Đếm row các bảng §6 ... bằng role `postgres` qua `docker exec`") and Success Criteria (`--local` 4 mục PASS thật)
- **Flaw:** The smoke script requires `postgres` **superuser** DB access on the prod host to count rows "RLS không che được." The runbook already documents that the prod DB has *no host port mapping* and is only reachable from inside the compose network (`docs/runbook-deploy.md:49-56`), so the script must `docker compose exec` into a container that holds superuser creds. The plan does not scope this to a least-privilege read-only role, nor note that shipping a script that runs arbitrary `psql` as `postgres` on the prod host widens what a compromised script/operator shell can do (full DB read/write/drop). "RLS không che được" is stated as a feature, but bypassing RLS from a smoke test is precisely the capability an attacker wants.
- **Failure scenario:** ops-smoke.sh is committed and run on the prod host by an operator whose shell is later compromised (or the script is modified in a PR). Because it already establishes a superuser `psql` channel into the prod DB, the compromise inherits full DB control rather than read-only visibility.
- **Evidence:** Phase 3 mục 6 (role `postgres`); `docs/runbook-deploy.md:49-56` (DB not host-exposed; superuser access is via in-network container); `docs/runbook-uat-golive.md:50,56` (row counts "bằng role `postgres`").
- **Suggested fix:** Use a dedicated read-only role for row counts (a `SELECT`-only grant on the §6 tables) rather than the `postgres` superuser. If RLS visibility is genuinely required, use `SET ROLE` to a role with `BYPASSRLS` scoped to read, not the cluster superuser. Document the exact role and its grants in the script header.

## Finding 4: "Prod-config local" journey runs contradict the boot-checks, and Phase 5's CI wiring quietly forces a real `STAFF_SESSION_SECRET` into the pipeline
- **Severity:** High
- **Location:** Phase 4 "Non-functional" ("Chạy trên stack prod-config local"), Phase 5 Success Criteria ("xanh ... trên stack prod-config local") and plan.md "Câu hỏi chưa giải" #2
- **Flaw:** Journeys mint staff cookies via `mintStaffCookie` (`apps/e2e/src/session-injection.ts:139-158`), which forges arbitrary roles — the existing bootstrap forges `roles: ['super_admin']` (`apps/e2e/src/global-setup.ts:110`). For a cookie to verify, the API and the minting side must share `STAFF_SESSION_SECRET`. But in `NODE_ENV=production` the API **refuses to boot** with the dev-default secret: `boot-checks.ts:135` (`if (secret === STAFF_SESSION_SECRET_DEV_DEFAULT) ... FATAL`) and `:128-131` (unset → FATAL). So "prod-config local" is only reachable by setting a real non-default `STAFF_SESSION_SECRET` on both sides. The plan asserts prod-config as if it were free, and Phase 5 open-question #2 punts the CI-wiring decision — but the moment journeys run in CI as "prod-config," CI must inject a non-default `STAFF_SESSION_SECRET`. That secret then lives in CI env and is one `set -x`/echo/`env` dump away from the logs, and it is the exact secret that forges valid staff sessions (including super_admin). The current e2e CI job sets **no** `STAFF_SESSION_SECRET` (`.github/workflows/ci.yml` e2e env block, lines ~120-155), i.e. it runs on the dev default and is *not* prod-config — the plan's claim is inconsistent with the pipeline it will extend.
- **Failure scenario:** Journeys are wired into a new prod-config CI job with a real `STAFF_SESSION_SECRET` injected. A future debug step (or a third-party action logging env) prints it; anyone with read access to CI logs can mint a super_admin staff cookie against any deployment sharing that secret. Alternatively the secret is reused from prod, turning CI-log read access into prod session forgery.
- **Evidence:** `apps/api/src/boot-checks.ts:128-137` (prod refuses unset/dev-default staff secret); `apps/e2e/src/session-injection.ts:139-158` (mint forges any roles); `apps/e2e/src/global-setup.ts:110` (super_admin bootstrap); `.github/workflows/ci.yml` e2e job env (no `STAFF_SESSION_SECRET`; currently dev-default / not prod-config).
- **Suggested fix:** State explicitly that journey CI uses a **throwaway, job-scoped** `STAFF_SESSION_SECRET` that is never a prod value, injected via masked secret, with `set -x` forbidden (same discipline Phase 3 already applies to curl). Resolve open-question #2 before Phase 5 rather than after: either run journeys in a dedicated prod-config job with a generated ephemeral secret, or drop the "prod-config" requirement for CI and keep it a local-only gate. Fix the plan's factual claim that prod-config is the same as the current e2e job.

## Finding 5: The `screen-role-expectations.ts` and journey specs commit an enumerated internal path→role→procedure map — the exact recon surface D4 quarantined
- **Severity:** Medium
- **Location:** Phase 1 "Related Code Files" (`Create: apps/e2e/src/screen-role-expectations.ts`) and Phase 4/5 committed journey specs
- **Flaw:** The `260717-1213` plan explicitly classified the Builder tab / raw symbol+route+model listing as sensitive — "bản đồ recon API nội bộ" that must never leave the repo boundary, and gitignored capture output before writing capture code (`plans/260717-1213-so-nghiem-thu-song/plan.md:45,95`). Phase 1 now creates `screen-role-expectations.ts` as **committed source** enumerating `(path, role, nonEmpty: procedure[])` — i.e. which internal tRPC procedures each screen calls per role — and Phases 4/5 commit journey specs that name procedures, nav labels, and SoD-forbidden paths. This is the same internal API map, just relocated from a gitignored artifact into tracked source. The plan's own runtime `capture-output/` is correctly gitignored (`apps/e2e/.gitignore:1`), showing the team already treats this data as non-public — yet the expectations file re-exposes a curated slice of it in a tracked file.
- **Failure scenario:** Repo access (contractor, leaked clone, or a public-mirror mistake) hands an attacker a hand-curated `screen→role→procedure` map plus SoD boundaries (which role is *forbidden* from approving) — a ready-made privilege-escalation target list, exactly what D4 decided must not be forwarded.
- **Evidence:** `plans/260717-1213-so-nghiem-thu-song/plan.md:45` (D4: internal API map must not leave the boundary), `:95` (recon-map risk accepted only under D4 quarantine); `apps/e2e/.gitignore:1` (`capture-output/` gitignored — same data class); Phase 1 Related Files (expectations committed); `apps/e2e/screen-role-matrix.json` already tracked (partial precedent).
- **Suggested fix:** This is likely acceptable given `screen-role-matrix.json` is already tracked, but the plan must make the call explicitly rather than silently: state that the path→role→procedure map is treated as internal-but-repo-tracked (consistent with the matrix), and confirm no journey artifact/report is ever rendered into a shareable/`--inline` document. Do not let expectations or journey output feed the `acceptance:report --inline` path that D4 quarantined.

## Finding 6: Falsification steps that mutate `packages/auth/src/index.ts` and nav-registry locally have a real "committed widened registry" failure mode the mitigation under-covers
- **Severity:** Medium
- **Location:** Phase 1 step 4 (Falsification A: "gộp lại `class.read` vào `class.create` trong registry (KHÔNG commit)"), Phase 2 step 4 (edit a nav entry, push to a branch), Phase 4 step 6 (hide a nav entry locally)
- **Flaw:** Three phases instruct the implementer to locally weaken the permission registry or nav visibility to prove the detector fires, relying on "KHÔNG commit / Hoàn nguyên." The plan's only backstop is the whole-plan AC `git diff packages/auth/src/index.ts` empty (plan.md:79) and Phase 1 risk row ("Falsification quên hoàn nguyên registry — Cao nếu xảy ra"). But Phase 2 step 4 explicitly **pushes** a branch with a mutated nav entry to prove the CI warns — a widened/incorrect registry state briefly exists on a remote branch, and the AC only checks `packages/auth/src/index.ts` at plan close, not the nav-registry or intermediate pushed commits. The rules file `review-audit-self-decision.md` ("Stable Code Artifacts") and the invariant "ĐO quyền, không SỬA quyền" (plan.md:65) both depend on this never leaking, yet the process deliberately creates the leak on a branch.
- **Failure scenario:** Phase 2's falsification branch (mutated nav entry) is merged or cherry-picked by mistake, or Phase 1/4's local registry merge is committed during a hurried `git commit -a`. A widened permission (`class.read` folded into `class.create`, or a hidden nav entry) reaches main; the very class of authz-visibility bug this plan exists to catch is introduced *by the plan's own falsification procedure*, and the closing AC (which only greps `packages/auth/src/index.ts`) may not catch a nav-registry or e2e-side change.
- **Evidence:** Phase 1 step 4 & risk row 4; Phase 2 step 4 (push a mutated entry); Phase 4 step 6 (hide entry locally); plan.md:79 (AC greps only `packages/auth/src/index.ts`); `.claude/rules/review-audit-self-decision.md` "Stable Code Artifacts."
- **Suggested fix:** Perform all falsification on a throwadway local worktree/stash that is never pushed; forbid pushing falsification branches (Phase 2 can prove the CI step on a local `act` run or a clearly-labeled ephemeral branch that is force-deleted). Broaden the closing AC to assert a clean diff on `apps/admin/src/shell/nav-registry.ts` and `apps/e2e/screen-role-matrix.json` as well, not just `packages/auth/src/index.ts`.

## Finding 7: No CI artifact upload today masks the leak surface the plan is about to grow — but the plan never states the "no upload" invariant
- **Severity:** Medium
- **Location:** Phase 1 step 3 (write findings to JSON output), plan.md invariant "không PII vào artifact" (plan.md:69)
- **Flaw:** The plan asserts an invariant "no PII into artifacts" but provides no mechanism or check to enforce it, and does not record *why* it currently holds. It holds today only incidentally: `.github/workflows/ci.yml` has **no `actions/upload-artifact` step** (grep for `artifact`/`upload` returns nothing), and `capture-output/` is gitignored (`apps/e2e/.gitignore:1`). The new findings arrays (`emptyButExpected`, `silentScreens`) and journey failure output will contain seeded business data (student names, receipt codes, employee rosters — Phase 4 F1/F4 assert non-empty rosters and receipts by displayed name). The instant anyone adds an artifact upload to debug a flaky journey (a very likely next step given Phase 4/5's flaky-risk emphasis), that seeded PII-shaped data becomes downloadable from CI. The invariant is a sentence, not a guardrail.
- **Failure scenario:** A future engineer debugging Phase 5 flakiness adds `upload-artifact` for the Playwright trace + capture JSON. Traces embed rendered screens (rosters, receipts, grades) and the JSON embeds seeded records. The "no PII into artifact" invariant is silently violated because nothing enforces it.
- **Evidence:** `.github/workflows/ci.yml` (no upload-artifact step present); `apps/e2e/.gitignore:1` (`capture-output/` gitignored); Phase 4 requirements (assert non-empty roster/receipt lists by displayed identity); plan.md:69 (invariant stated, unenforced).
- **Suggested fix:** Convert the invariant into a checkable rule: seed with clearly-synthetic non-PII identities only (already partly true via `synthetic-seed-env.sh`, so state it), and add a note/guard that any future `upload-artifact` for these specs must scrub or must retain only synthetic data. If Playwright traces are ever uploaded, mask them or restrict artifact access. State the enforcement, not just the intent.
