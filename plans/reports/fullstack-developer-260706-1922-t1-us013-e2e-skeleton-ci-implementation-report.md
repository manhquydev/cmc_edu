## How server-spawn / auth / OTP-read were wired

**Server spawn.** `global-setup.ts` finds a free port (`node:net`, listen(0) probe), then spawns `node <resolved tsx/cli> apps/api/src/server.ts` (`createRequire(import.meta.url).resolve('tsx/cli')` — cross-platform, no shell/`.cmd` wrapper needed) with `PORT`/`APP_DATABASE_URL` in its env, forwarding the rest of `process.env`. Polls `GET /health` (up to 20s) before proceeding. Playwright's `globalSetup` returning a function is used as the built-in teardown mechanism (kills the child, then calls `cleanupFacility`) — no separate `globalTeardown` file needed. State (`E2E_BASE_URL`, `E2E_FACILITY_ID`) is passed to test workers via `process.env` mutation in the setup process (Playwright forks workers from that same env).

**Facility bootstrap.** `facility.create` under a `super_admin` `x-dev-user` header — `requireValidFacility` (apps/api/src/trpc.ts) unconditionally bypasses for `super_admin`, and `facility.create` itself never calls `scoped(ctx)` (Facility carries no RLS), so the header's `facilityId` field is a required-but-unused placeholder (`'bootstrap'`) just to satisfy the dev-header zod schema.

**Auth.** `src/trpc-client.ts` wraps `@trpc/client`'s `httpBatchLink` with a `headers()` callback setting `x-dev-user`/`x-dev-lms-user` (JSON, matching `apps/api/src/context.ts`'s dev-auth stub exactly) per client instance — `createStaffClient`/`createLmsClient`/`createAnonClient`. `AppRouter` is imported `type`-only from `../../api/src/router.ts` (a plain relative import, no package `exports` entry exists for `@cmc/api` since it's an app not a lib) so every call is fully typed against the real router. To keep turbo's build-before-typecheck graph correct for this cross-app type-only import, `@cmc/domain-finance`/`@cmc/domain-identity` were added to `apps/e2e`'s `package.json` (the former as a devDependency purely for the graph edge; the latter is also used at runtime for `normalizeLoginPhone`).

**OTP read.** `LoginOtp.codeHash` stores `${salt}:${sha256(salt+code)}` (apps/api/src/lms-auth/otp-hash.ts) — the plaintext is never persisted and there is no existing seam that returns it. `db.ts`'s `readOtpCode` re-hashes all 10^6 six-digit candidates against the stored salt+digest (sub-second) to recover the code — a DB read + client-side inversion, no server code touched.

**Active enrollment (attendance spec).** Rather than re-running the full CRM->receipt->approve provisioning pipeline (already exercised end-to-end by `enrollment.spec.ts`), the attendance spec seeds a Student + already-`active` Enrollment directly via `db.ts`'s `seedActiveEnrollment` — mirroring the exact pattern `apps/api/src/test/db.ts`'s own `seedActiveEnrollment` already uses for the attendance gate's integration tests, since the attendance gates (not enrollment provisioning) are what this spec targets.

## Assumptions
1. `APP_DATABASE_URL`/`DATABASE_URL` are expected to already be exported in the shell environment running `pnpm --filter @cmc/e2e test` — same expectation `apps/api/src/test/db.ts`'s integration tests already have (no `.env` loader exists anywhere in `apps/api`/`apps/e2e`). `global-setup.ts` throws a clear, actionable error if `APP_DATABASE_URL` is missing.
2. No decision doc pins a CI Postgres image/creds — used `postgres:16` (matches `docs/system-architecture.md`'s dev stack) with throwaway CI-only credentials (never a real secret) and `ALTER ROLE cmc_app WITH PASSWORD` after `prisma migrate deploy` (the migration creates the role with no password by design — `packages/db/prisma/migrations/20260706054322_.../migration.sql` comment: "set one out-of-band per environment").
3. e2e is wired into CI as its own job with `continue-on-error: true`, NOT part of the blocking `typecheck-and-test` gate — per the phase brief ("e2e vào CI ở PD"; "OK to gate on typecheck+test first if e2e-in-CI is flaky"). Promoting it to blocking is a follow-up once proven stable in CI.
4. `classBatch.create`'s `startDate`/`endDate`/`slots` values in both specs don't need to actually generate `ClassSession` rows via the weekday-matching auto-generator (`sessionsCreated` may be 0) — sessions are created directly via `classSession.addMakeup` instead (the only session-creating procedure that returns the created row's id; there is no `classSession.list`/`get` query endpoint).
