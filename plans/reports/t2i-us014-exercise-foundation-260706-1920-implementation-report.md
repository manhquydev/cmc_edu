## Upload route design note (deviation, documented per instructions)

The spec calls this an "HTTP multipart route." I implemented it as a raw-body POST with `Content-Type:
application/pdf` (the body IS the PDF bytes), not a literal `multipart/form-data` parse. Reasoning: (1) the repo
has no multipart-parsing dependency and none was requested to be added; (2) the acceptance criterion is
"validate mime application/pdf" — a real `multipart/form-data` request's `Content-Type` is
`multipart/form-data; boundary=...`, which would never equal `application/pdf`, so the literal spec wording only
makes sense against a raw-body PDF upload; (3) YAGNI — the WF-P2-04 doc text just says "giao diện upload" (an
upload UI), not a literal multipart form. `createHTTPHandler` (not `createHTTPServer`) is used in `server.ts` so
the upload route and tRPC share one `http.createServer`, per the confirmed `@trpc/server` v11 pattern (WebSearch,
trpc.io/docs/server/adapters/standalone — `createHTTPHandler` returns just the request listener for composition).
